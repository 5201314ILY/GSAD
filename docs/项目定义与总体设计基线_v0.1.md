# 广义流矢解码 — Generalized Stray-Arrow Decoding（GSAD）

> 产品定位：通用数据处理与存储引擎。项目名称已由 ADR-0003 确立。
## 项目定义与总体设计基线 v0.1

- 文档状态：讨论基线，尚非冻结的工程规范
- 版本：0.1
- 目标：在正式编码前，统一项目使命、边界、架构原则、模块责任和实现顺序
- 命名说明：GSAD 已作为项目名称确立；USF（Unified Storage Format）仅可作为未来某一种可选存储格式的工作代号，不能代表整个项目。

---

## 0. 一页版定义

本项目要构建一套**通用数据处理与存储引擎**。它能够读取、识别、解析、转换、压缩、解压、解码、验证、索引和存储多种类型的数据，并根据数据特征、使用场景和性能目标，选择合适的算法、处理链与物理存储布局。

它不是单独的压缩器，不是单独的万能解码器，不是把若干开源库包在统一 API 外面的薄封装，也不是以 AI 为唯一目标的平台。

它的核心思路是：

1. **统一管理机制，不统一所有算法。** 统一任务、资源、错误、插件、权限、缓存和可观测性；保留文本、二进制、媒体、网络协议、压缩和密码学等领域各自的专业机制。
2. **统一能力契约，不强迫统一实现。** 各引擎声明输入输出类型、参数、限制和能力，系统据此组合可行的处理流程。
3. **支持多种存储策略。** 不同文件、数据块和访问模式可以选择不同的物理布局；统一元数据和管理能力不等于把所有数据放进同一种格式。
4. **原始数据、变换结果和解释结果分层保存。** 原始字节应能保留；解压结果、媒体帧、解析树、索引和语义分析是不同类型的产物，不能相互混淆。
5. **性能和安全是核心设计，不是后期补丁。** 有界内存、背压、取消、随机访问、完整性、崩溃恢复、恶意文件防护和资源配额都属于基本要求。
6. **开源项目是研究对象和可选实现来源，不是架构的主人。** 先确定需求和接口，再决定复用、适配、替换或自主实现什么。
7. **AI 是重要应用方向之一，而非项目存在的唯一理由。** 即使不加载任何模型，软件也应能独立完成有价值的数据处理工作。

## 1. 项目使命、用户与交付物

### 1.1 项目使命

建立可组合、可扩展、可测量、可恢复、可审计的数据处理基础设施，使不同格式和算法能够通过一个稳定的系统协同工作，而不需要被迫采用相同算法、相同存储布局或相同运行方式。

### 1.2 主要使用场景

- 本地文件和目录的读取、识别、检查、转换和批处理。
- 压缩包、归档、固件、磁盘镜像和大型二进制数据的处理。
- 文本、源码、日志、结构化文档和配置数据解析。
- 图片、音频、视频和多媒体容器的读取、解码、转封装与元数据提取。
- 经授权的网络流量、协议报文和协议载荷分析。
- 具有合法密钥与授权的加密数据解密、认证和完整性检查。
- 大型数据集的分块、索引、去重、版本化、缓存和高效读取。
- 为开发工具、自动化工作流、数字取证研究和 AI 应用提供底层数据能力。

### 1.3 计划交付物

项目成熟后应至少具备：

- 核心运行库与稳定的公共 API。
- 可扩展的格式/算法插件协议。
- 命令行工具，用于检查、转换、压缩、解压、验证和诊断。
- 一组参考实现和示例插件。
- 可选的统一存储库/容器实现；不强制所有数据都使用该容器。
- 自动测试、模糊测试、基准测试、崩溃恢复测试和安全限制测试。
- 文档、格式说明、兼容性策略、依赖清单和许可证清单。
- 后续可选的 SDK、图形界面、服务端接口和 AI/REA 适配器。

## 2. 范围与非目标

### 2.1 项目范围

**A. 数据来源与 I/O**：普通文件、内存缓冲区、流式输入、可选的 HTTP/对象存储等后端；具备顺序读取、偏移读取、探测能力、取消和超时等语义。

**B. 数据识别与结构处理**：基于签名、内容探测和可选的调用方提示来识别格式；支持文本编码、容器结构、二进制字段和协议报文解析。

**C. 变换引擎**：压缩/解压、字符集转换、加密/解密、校验、媒体解码、格式转换和结构化提取。每种变换必须明确自己的语义和限制。

**D. 存储与索引**：原始对象、分块、压缩帧、元数据、索引、缓存、版本和完整性信息；允许多种后端和布局。

**E. 编排与执行**：将操作组成可验证的任务图，执行依赖顺序，提供并发控制、资源配额、背压、取消、超时和日志。

**F. 扩展与集成**：通过插件/适配器连接专业库，例如 7-Zip/LZMA SDK、FFmpeg、SQLite、密码学库、二进制解析工具和 REA。

### 2.2 非目标（至少不是第一阶段目标）

- 不承诺第一版支持所有已知文件格式和所有网络协议。
- 不从零发明所有压缩算法、密码学算法和媒体编解码器。
- 不把每个外部项目的源代码合并进同一个代码仓库，作为整合的前提。
- 不强迫所有文件使用同一压缩算法或同一种自有容器。
- 不把压缩包、数据库、媒体流、协议和加密数据统统称为同一种“解码任务”。
- 不承诺能在没有正确密钥、授权或必要上下文的条件下解密任意加密数据。
- 不以训练新的基础大模型作为早期里程碑。
- 不以反编译/逆向功能取代核心数据引擎；REA 是可集成的分析工具，而不是整个项目的底座。

## 3. 已确立的设计原则

### 3.1 原始数据优先保真

系统必须能够保留源字节并记录来源、大小、校验值和处理历史。解析出的文本、帧、字段、缩略图、索引或 AI 结果均应作为派生产物与源数据建立可追溯关系。除非调用方明确选择覆盖或丢弃，不应静默替换原件。

### 3.2 区分识别、解析、解码、解压、解密和语义解释

这些属于不同操作：

- **格式识别**：猜测或确认输入可能遵循什么格式；识别结果应带置信度，不能假装百分之百确定。
- **结构解析**：从字节读取字段、长度、索引、时间戳或协议结构。
- **字符解码**：例如将 UTF-8 字节转换为字符。
- **解压缩**：把压缩表示恢复为压缩前的数据。
- **密码学解密/认证**：需要相应密钥和算法参数；对于认证加密，认证失败必须作为失败处理，不得把未经认证的输出当作可信结果。
- **媒体解码**：将编码媒体数据解码为帧、采样或其他规范化表示。
- **语义提取**：例如从文档、数据库或二进制结构中抽取更高层信息。

处理顺序必须根据具体格式或协议确定，不应使用一个固定的全局顺序套用所有数据。

### 3.3 统一调度，不强制线性流水线

许多任务适合流水线，但系统本身应支持有向任务图（DAG）：一个任务可以有多个输入、多个产物、分支、条件步骤和依赖。需要顺序处理时使用流式执行，需要随机访问时使用索引和偏移定位，需要独立处理时可并行运行。

“水库/水管/水锤阀”只是一组帮助思考数据流、缓存和背压的比喻，不是硬性架构。双缓冲只是可选优化；共享缓存、批量读取、预读或多缓冲是否有效，必须依据负载和测量决定。

### 3.4 多种存储布局并存

统一管理接口应能容纳至少下列策略：

- 原始/直通存储：不再压缩或转换。
- 面向顺序访问的流式存储。
- 带索引的分块或压缩帧存储。
- 面向随机读取的页/块布局。
- 内容寻址和去重存储。
- 面向频繁修改的增量或版本化存储。
- 面向媒体或其他专用数据的优化布局。

单个对象的存储策略应由压缩收益、访问模式、更新频率、随机访问要求、保密性和资源预算综合决定。统一容器若被实现，应是可选后端之一，而不是所有数据唯一的宿主。

### 3.5 复用与自研并重

优先自研真正构成项目差异化的部分：统一能力契约、任务计划器、资源调度、缓存与 I/O 协同、数据/产物关系、存储策略选择、可观测性、安全边界和一致性协议。

对已经成熟且复杂的专业算法，优先通过稳定适配器复用。只有在有清楚的性能、许可、平台或架构理由时，才考虑重写算法或深度分叉外部项目。

### 3.6 可插拔必须有约束

插件不是任意代码直接进入核心的借口。插件需要声明能力、版本、依赖、资源特征、可信级别和权限；不可信或风险较高的解析器应能放入独立进程/沙箱运行。

## 4. 统一架构

### 4.1 分层与模块边界

1. **应用接口层**：CLI、SDK、后续图形界面和服务接口。
2. **任务与编排层**：任务图、依赖解析、并发调度、取消、超时、重试策略和作业状态。
3. **能力注册与计划层**：发现可用引擎，检查输入输出兼容性，选取可行的处理链并评估成本。
4. **专业处理引擎层**：文本、二进制、归档、压缩、媒体、网络协议、密码学、数据库、文档等。
5. **I/O 与存储抽象层**：ByteSource/ByteSink、随机读取、流式读取、存储后端、分块映射和物理布局。
6. **元数据与索引层**：对象元数据、内容哈希、格式探测结果、分块位置、处理记录、版本和恢复状态。
7. **横切基础设施**：内存预算、缓冲池、缓存、校验、日志、指标、审计、授权、崩溃恢复和诊断。

这些是职责边界，不是说系统必须拆成七个进程。初期可以是一个进程、模块化单体；有需要时再将风险较高的插件或重负载引擎隔离成独立进程。

### 4.2 核心模块建议

| 模块 | 责任 | 明确不负责 |
|---|---|---|
| `core` | 公共类型、生命周期、错误、取消、版本约定 | 不内置所有格式细节 |
| `capabilities` | 注册能力、约束与版本、输入输出匹配 | 不执行昂贵处理本身 |
| `planner` | 构建和验证任务图、选择可行路径 | 不猜测无法证明的格式事实 |
| `scheduler` | 并发、配额、优先级、背压、取消和公平性 | 不决定算法的语义 |
| `io` | 顺序/随机 I/O、读写适配器、超时 | 不解压或解析数据 |
| `storage` | 物理对象、分块、布局、持久化及恢复 | 不把一种布局硬塞给所有数据 |
| `metadata` | 对象、索引、来源和转换记录 | 不存放大型数据主体的唯一副本 |
| `transforms` | 可组合的数据变换契约 | 不混淆解码、解压与解密 |
| `formats` | 文件/容器/文档/二进制格式解析 | 不自行实现通用调度 |
| `protocols` | 协议分帧、流状态和消息解析 | 不默认有能力解密所有传输 |
| `crypto` | 经审查的密码学库适配、安全参数和密钥接口 | 不自创密码算法、不记录明文密钥 |
| `media` | 媒体容器与编解码器适配 | 不将媒体帧语义推广到普通文件 |
| `plugins` | 插件发现、加载、能力和隔离策略 | 不允许无约束地访问主机资源 |
| `audit` | 来源、证据、操作历史与诊断记录 | 不把推测当作原始事实 |
| `adapters/rea` | 与 REA CLI/MCP 进行受控集成 | 不成为核心引擎运行的硬依赖 |

## 5. 统一能力契约

每个引擎/插件至少描述：

- `id`、版本、供应方、许可证和依赖。
- 输入类型与输出类型，以及可识别的格式标识。
- 支持的操作：探测、解析、编码、解码、压缩、解压、验证、提取等。
- 运行模式：流式、随机访问、增量、批处理、同步或异步。
- 是否支持取消、超时、部分结果和恢复。
- 有损/无损、是否可逆、是否保留原始数据。
- 资源特征：估算内存、线程能力、CPU 特性、最大输入/输出限制。
- 安全属性：需要的文件/网络/密钥权限、是否必须隔离运行。
- 错误类型、可恢复性、校验方式和诊断信息。

能力声明只是一个起点，运行时仍需验证插件行为；声明不应替代沙箱与资源限制。

## 6. 处理模型与典型任务

### 6.1 处理任务图

一个处理步骤可以抽象为：输入对象 + 明确参数 + 能力版本 + 资源预算 -> 输出对象/产物 + 状态 + 诊断信息。产物应记录其父对象、变换链和关键参数，方便复现与追踪。

规划器必须区分“格式事实”和“探测猜测”。当输入不明确时，应允许输出候选格式及置信度、请求调用方指定格式，或采用只读探测；不能默默选择风险最高的分支。

### 6.2 典型处理链示例

- 文本：源字节 -> 字符集探测/用户指定 -> 字符解码 -> 可选语法解析 -> 文本索引。
- 归档：文件读取 -> 容器解析 -> 条目索引 -> 按需解压单个条目 -> 校验 -> 输出。
- 网络：捕获/输入流 -> 协议分帧 -> 必要时基于合法凭据处理加密层 -> 内容编码解压 -> 文本/二进制解析。
- 媒体：字节源 -> 容器解复用 -> 选择媒体流 -> 解码帧/采样 -> 可选变换或转封装。
- 加密对象：读取加密数据 -> 解析算法参数与 nonce/标签等元数据 -> 使用正确密钥执行解密和认证 -> 认证成功后将输出交给下一个阶段。
- AI/REA 分析：选择目标 -> 检查权限和预算 -> 执行工具 -> 接收原始结果与证据 -> 规范化存档 -> 关联源对象和限制 -> 可选进一步验证。

处理链不固定；例如，某些格式要求先解析容器才能定位压缩流，而另一些格式则先进行解压才能识别内部格式。

## 7. 存储设计基线

### 7.1 逻辑模型与物理布局分离

逻辑对象包含身份、来源、逻辑大小、格式/媒体类型、完整性信息、版本、标签和相关产物。物理存储记录对象实际位于哪个后端、哪个包/块、什么偏移和什么编码形式。

不能让 SQLite 表结构决定物理文件布局，也不能让某一种压缩算法决定整个仓库的对象模型。

### 7.2 可能的数据记录

概念性对象字段可包括：

- `object_id`：逻辑对象标识。
- `content_hash`：按指定算法计算的内容校验/寻址值。
- `logical_size`：逻辑数据大小。
- `media_type` / `format_id`：媒体类型和格式标识，允许未知值。
- `source_ref`：来源对象或外部来源引用。
- `storage_profile`：所采用的存储策略。
- `physical_refs`：块/包/后端位置引用。
- `integrity_state`：未检验、通过、失败或未知。
- `created_at`、`version`、`metadata_version`。

概念性数据块记录可包括：`chunk_id`、逻辑/物理大小、压缩方法、字典标识、校验算法与值、加密配置引用、物理位置和标志位。以上均为设计草案，不是最终二进制格式规范。

### 7.3 存储类别

- **Raw**：原始内容原样存放，适合不可压缩、对字节保真敏感或需要直通读取的数据。
- **Stream**：适合顺序读写与低延迟处理。
- **Indexed chunks**：适合较大数据、随机读取和并行解码。
- **Mutable indexed store**：适合高频修改、事务和索引访问。
- **Content-addressed store**：适合版本化和去重，但必须考虑隐私泄漏、哈希选择与删除语义。
- **Specialized layout**：为媒体、只读镜像或其他特殊负载进行优化。

对象或对象分区可以按需求选择布局；不要一开始就实现全部布局，先通过基准测试证明必要性。

### 7.4 事务与崩溃一致性

如果数据主体和元数据索引分别存储，它们之间通常不存在天然的单一原子事务。建议的基本写入顺序是：

1. 写入数据块/数据包到临时位置。
2. 校验数据并按后端能力执行必要的持久化操作。
3. 在元数据事务中提交位置映射和对象记录，使对象变为可见。
4. 清理遗留临时文件/孤儿块，并定期进行一致性扫描。

恢复程序必须能识别未完成写入、不可达数据和指向不存在数据的元数据。正式实现前需要明确每个后端的持久化保证，不能把 `flush` 等同于所有平台上的可靠落盘。

SQLite 可以作为早期本地元数据目录和事务索引的候选。SQLite VFS 是其操作系统 I/O 抽象接口；WAL 有本机并发优势，但官方文档明确指出 WAL 依赖同一主机共享内存，不能当作网络文件系统上的多主机协调方案。因此本项目的多主机协调将来若需要，应另行设计锁/租约/服务端一致性协议。SQLite 不必成为永久唯一的元数据引擎。

### 7.5 USF 是否需要

先不冻结 USF 的二进制格式。只有在明确出现统一对象容器的真实需求后，再制定格式 RFC，至少验证：

- 格式版本和向前/向后兼容策略。
- 损坏检测、恢复与部分读取。
- 索引放在头部、尾部还是独立索引文件，以及更新成本。
- 数据校验、加密认证和密钥元数据布局。
- 压缩帧/块边界与随机访问的关系。
- 扩展字段、未知字段跳过和未来格式迁移。
- 崩溃恢复、原子替换和并发读写语义。

早期可先用现有文件格式或目录布局验证系统核心，不要把“先发明文件格式”变成阻塞核心架构验证的步骤。

## 8. 压缩、解码和密码学策略

### 8.1 压缩策略

不要只按压缩率评价算法。至少要评估压缩率、压缩速度、解压速度、内存、线程效率、局部随机访问能力、字典依赖、增量处理成本以及许可证。

候选技术方向：

- 快速通用无损压缩：Zstandard、LZ4 等。
- 高压缩率和字典类方法：LZMA/LZMA2、XZ 等。
- 兼容性或专用格式要求：Deflate、Brotli 以及归档内既有算法。
- 分帧与索引：研究独立压缩帧/seek table 等思路，使部分读取不必解压全部数据。
- 结构感知方法：针对文本、日志、表格或特定二进制格式，经基准测试后再增加专用编码器。

已压缩或加密的数据通常不值得再盲目压缩。可先进行采样/快速试压缩估计收益，但决策本身也要计入 CPU 与延迟成本。加密一般会降低可压缩性，因此常见顺序是先压缩再加密；是否跨对象去重还要考虑隐私和安全影响。

### 8.2 解码与解析策略

建立专用引擎和能力描述，不建立一个“万能解码器”。对于二进制结构，可以研究声明式格式描述；对于网络协议，可以研究分帧、流重组和状态机；对于媒体，应把容器解复用和音视频编解码分开处理。

### 8.3 密码学策略

密码学不是普通压缩，也不是只要“解码”就能还原。必须使用正确密钥、算法、nonce/IV、认证标签和协议上下文。项目不应自创加密算法；应优先采用经审查的成熟实现，并将密钥管理、权限、认证失败、秘密数据日志和内存清理作为独立安全设计。未经授权的密文分析不属于默认工作流。

## 9. 运行时、I/O、缓存与背压

### 9.1 I/O 能力契约

最低限度区分：

- 顺序读：`read`。
- 按偏移读取：`read_at`（支持情况必须明示）。
- 长度/尺寸探测：`size`（未知长度允许显式表示）。
- 定位：`seek`（说明可定位范围和代价）。
- 写入、冲刷、关闭：`write`、`flush`、`close`。
- 可取消、可超时、可报告短读/EOF/暂时不可用等状态。

网络流、压缩流和普通文件并非都支持随机访问。调用方必须能够查询能力，而不是默认所有源都是 seekable。

### 9.2 资源与背压

调度器要使用有界队列和资源预算。下游处理速度低于上游时，应减少预读、降低并发或暂停生产，而不是无限堆积内存。任务需要支持取消、超时和公平调度。

双缓冲、多缓冲、批量 I/O、I/O 合并、预读、压缩数据缓存和解码结果缓存都作为按场景启用的优化。必须通过性能指标证明其收益，并有内存上限和失效策略。

### 9.3 缓存分层

- 元数据与格式探测缓存。
- 压缩/原始字节块缓存。
- 解码后数据缓存。
- 可选的解析结果和索引缓存。

不同缓存应有不同失效规则和预算。涉及密钥或敏感明文的内容，必须考虑是否禁用缓存、缩短生命周期或进行更严格的内存隔离。

## 10. 公共 API 草案

API 名称不是冻结的最终接口，但语义必须明确。初期可围绕下列形态设计：

- `engine_create(config)` / `engine_destroy(engine)`
- `source_open(uri, options)` / `source_close(source)`
- `source_read(source, buffer, size)` / `source_read_at(source, offset, buffer, size)`
- `probe_format(source, hints)`
- `capability_list(filter)`
- `job_plan(operation, input, options)`
- `job_submit(plan)` / `job_wait(job)` / `job_cancel(job)`
- `artifact_open(artifact_id)` / `artifact_read_at(...)`
- `object_store_put(...)` / `object_store_get(...)` / `object_verify(...)`
- `plugin_register(...)` / `plugin_inspect(...)`

每个 API 需要进一步定义：句柄生命周期、并发使用规则、所有权、缓冲区归属、错误码、短读语义、超时、取消、部分成功、进度回调、重入限制和版本兼容性。

不要让公共 API 直接暴露某个第三方库的内部结构体。适配层负责将外部库错误与对象转换成项目自己的错误和数据契约。

## 11. 安全、可靠性与隔离

任何输入文件、归档条目、协议载荷、脚本、反编译文本或远程返回内容，都应视为不可信数据，而不是可执行指令。

必须逐步建立：

- 最大输入、最大输出、最大解压倍率、最大嵌套深度和最大条目数限制。
- CPU、内存、线程、磁盘、网络和执行时间配额。
- 路径穿越、符号链接、覆盖文件、归档炸弹、畸形长度、整数溢出和资源耗尽防护。
- 插件权限声明；高风险解析器可在独立进程或沙箱中执行。
- 对网络和密钥访问的显式授权。
- 加密认证失败时拒绝把输出作为可信数据继续使用。
- 日志不记录密码、密钥和敏感明文；对秘密数据进行必要的生命周期管理。
- 模糊测试、畸形语料库、属性测试、崩溃注入和恢复验证。
- 所有第三方代码的版本、许可证、漏洞通告和升级记录。

REA 的使用应限定在拥有或获准分析的程序、数据和环境。其输出中的推断应与原始证据、限制和未验证部分分别记录；重要结论要能够复核。

## 12. REA 在整体中的位置

REA 是可选的分析工具适配器，不是基础数据存储层，也不是所有操作都需要运行的常驻解码器。适合的流程是：

1. 用户或更上层工作流提出一个有授权边界的分析任务。
2. GSAD 建立作业、资源限制与权限上下文。
3. `adapters/rea` 通过 REA 支持的 CLI/MCP 契约调用工具。
4. 保存原始工具返回值、标准化结果、证据标识、来源与限制。
5. 将结果作为派生产物关联到目标对象；必要时安排独立验证任务。
6. AI 可以在其之上做规划和总结，但 AI 不应覆盖原始证据或把推断伪装成已验证事实。

REA 当前公开文档描述其面向应用、原生二进制及运行行为分析，并提供 CLI/MCP 工作流及证据相关结果。其自身代码为 MIT 许可，但第三方工具和依赖继续受各自许可证约束；集成前必须复核具体版本的官方文档、许可证和外部工具条件。

## 15. 实施路线：先证明核心，再扩展格式广度

### 阶段 0：需求、ADR 与风险清单

产出：本文件的审阅版本、目标平台和语言候选、能力契约草案、威胁模型、第三方依赖/许可证策略、基准数据集规划。此阶段不宣称已完成软件。

### 阶段 1：最小核心闭环

实现一个可工作的模块化核心：统一错误与取消、ByteSource/ByteSink、任务模型、能力注册、基础格式探测、资源预算、日志/指标和自动化测试。先支持本地文件与内存源。

### 阶段 2：第一条真正的端到端路径

用一条有限但有代表性的路径验证架构：原始文件 -> 格式/压缩探测 -> 至少一种通用压缩/解压实现 -> 校验 -> 输出；同时覆盖 UTF-8 文本、基本二进制元数据和常见归档的单条目读取。明确哪些功能由外部成熟库实现，哪些由本项目核心实现。

### 阶段 3：可测量的存储与调度

加入有界缓冲、缓存、预读/背压策略、索引和随机读取原型；引入崩溃注入，证明写入顺序、元数据提交和恢复规则。只有测量结果显示必要时，再增加双缓冲和更复杂缓存。

### 阶段 4：专业引擎扩展

依次接入文本/文档、更多归档与压缩、二进制解析、密码学适配、网络协议与 FFmpeg 媒体适配。每一种新能力都必须通过统一契约和测试矩阵，不允许通过绕过核心来形成第二套不兼容架构。

### 阶段 5：可选统一存储容器

如果已有真实需求，再制定并实现 USF 或其他仓库格式；先写格式 RFC，再写读写器、损坏恢复、兼容性和迁移测试。

### 阶段 6：REA/AI 与更高层产品

把 REA 作为有授权、有资源限额、可审计的作业适配器接入。再考虑语义索引、AI 工作流、图形界面或服务化部署。AI 依赖不应成为普通数据处理功能的硬性前提。

## 16. 验收指标与测试原则

不预先虚构绝对性能数字。先构建稳定的测试语料和基线，再根据平台与目标负载设定指标。

- **正确性**：无损操作逐字节一致；媒体/有损操作按专用质量指标评测；格式解析与官方工具/已知样本交叉验证。
- **完整性**：损坏、截断、错误参数、错误密钥和认证失败都应以明确状态呈现。
- **性能**：记录吞吐、延迟分位数、CPU、峰值内存、磁盘读写、压缩率和随机读取放大。
- **扩展性**：新增插件无需修改所有核心模块；不兼容能力必须在规划阶段被拒绝或显式转换。
- **可取消性**：长任务应在约定范围内响应取消，不能无限卡死。
- **资源有界**：畸形文件、超大声明长度和解压炸弹不能无限消耗资源。
- **一致性**：在关键写入点注入崩溃后，恢复时不得把不完整对象呈现为有效对象。
- **兼容性**：公共 API 和自有持久化格式需有版本策略与回归测试。
- **安全性**：持续运行模糊测试，并为关键解析器保留语料回归。
- **可观测性**：能解释任务选用了哪些能力、为何选择、发生了什么错误、消耗了多少资源。

性能比较必须在相同数据、同等压缩级别/质量、相同硬件和可复现设置下进行，避免只比较单个压缩率或宣传数字。

## 17. 需要通过原型研究再决定的事项

这些选择现在不冻结：

1. 主语言及 FFI 边界（C/C++、Rust 或其他组合）。
2. 先做跨平台桌面工具还是先做库/CLI；目标操作系统顺序。
3. 采用单一模块化进程还是部分插件进程隔离。
4. 元数据后端选 SQLite 还是抽象化后可替换的后端。
5. 自有统一存储容器是否必要，以及 USF 的具体二进制布局。
6. 固定大小分块、内容定义分块（CDC）或两者并存。
7. 第一批支持的格式清单与明确的性能目标。
8. 缓存层次、预读、双缓冲和内存池的实际收益。
9. 插件 ABI、跨语言契约及版本兼容方法。
10. 加密对象的密钥管理方式及哪些操作可由核心提供、哪些只提供适配。

这些问题需要 ADR（架构决策记录）逐条解决：写清楚背景、候选方案、实验结果、决策和后果，而不是在聊天或代码中留下隐性决定。

## 18. 当前不可妥协的项目边界

- 不把 AI 当作整个软件的唯一目的。
- 不把“解码”当成一种统一算法；对每种数据选择适当的专业处理方法。
- 不把所有数据都强制存进一个统一的物理布局。
- 不把调用几个库或统一 API 包装误称为底层深度整合。
- 不为了追求自研而重写已有的安全关键算法。
- 不让第三方库的内部数据结构成为公共 API 的长期承诺。
- 不让解析、压缩或网络任务拥有无界内存、CPU、磁盘与权限。
- 不把探测、推断或 AI 生成的结论冒充原始数据与已验证事实。

## 本文件结论

项目应以“广义流矢解码（GSAD）”作为正式项目名称，并以“通用数据处理与存储引擎”描述产品定位。首要任务不是立刻写一个庞大的统一格式，也不是把所有第三方项目的代码合并，而是定义稳定的能力契约、处理任务模型、I/O 与存储抽象、安全和一致性基线，再通过小而完整的端到端原型验证这些核心设计。只有当这些基础经过测试，才逐步扩展压缩、二进制、文本、网络、密码学、媒体和 REA 等专业能力。
