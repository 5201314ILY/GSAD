# GSAD 工程规格：Core API、能力模型与任务执行契约

- 文档版本：v0.1
- 状态：设计草案，供原型验证与评审
- 项目名称：广义流矢解码 — Generalized Stray-Arrow Decoding（GSAD）；产品定位：通用数据处理与存储引擎
- 本文范围：统一数据源接口、能力注册、任务执行、错误模型、资源与安全规则
- 保留待验证的决策：最终插件 ABI、最终存储容器格式、默认压缩算法、完整 UI/API 服务形态

> 本文定义的是跨语言的工程契约与行为要求，不是已经实现的 API，也不代表所有细节都已通过性能测试。实现时可以调整名称和语法，但不能在未经评审的情况下破坏这里定义的语义。

---

## 1. 目标与非目标

### 1.1 本阶段目标

1. 让文件、内存、网络流和未来的存储对象能够通过明确的接口提供字节数据。
2. 让文本解码、格式解析、压缩/解压、媒体解码、协议处理、密码学处理等能力，以可描述、可组合、可测试的模块形式注册。
3. 让一次数据处理有明确的输入、处理步骤、输出、取消行为、资源上限和结果状态。
4. 让错误能够定位到具体阶段、偏移和失败类别，不再只有一条无法机器处理的错误字符串。
5. 让流式处理的队列和缓冲有界；下游变慢时能施加背压，取消时能尽快停止不必要的工作。
6. 为以后加入多种存储布局、外部专业库、REA、AI 与服务接口保留扩展点。

### 1.2 本阶段非目标

- 不创建一个声称能解析所有文件的万能解码器。
- 不要求所有数据经过完全相同的处理流水线。
- 不立即实现所有算法或所有文件格式。
- 不在未有基准数据的情况下承诺某个压缩率、速度或内存指标。
- 不在核心层自行发明密码学算法。
- 不在这一阶段确定并冻结自有容器格式。
- 不要求外部库都运行在同一个进程或采用同一种内部数据结构。

## 2. 核心术语

为避免将“文件、数据流、格式、解码”等概念混成一件事，内部设计先固定以下术语。

| 术语 | 定义 | 例子 |
|---|---|---|
| Byte Source（字节源） | 提供原始字节读取能力的对象；不承诺内容一定是文件 | 本地文件、内存缓冲、网络响应、存储对象 |
| Byte Sink（字节写入端） | 接收字节并明确结束、提交或放弃输出的对象 | 临时文件、对象存储、内存输出 |
| Data Object（数据对象） | 引擎管理的逻辑数据实体，可有一个或多个物理表示 | 原始视频、压缩数据集、解析后的文档 |
| Representation（表示形式） | 某份数据当前采用的可描述形式 | 原始字节、压缩字节、加密容器、解码后帧 |
| Capability（能力） | 可以被注册、发现、验证与调用的操作 | zstd 解压、UTF-8 解码、JSON 解析、视频解码 |
| Processor（处理器） | 执行一种或多种能力的模块 | 文本处理模块、FFmpeg 适配器 |
| Plan（执行计划） | 由若干操作与数据依赖组成的处理图 | 解密 → 解压 → 字符解码 → 文档解析 |
| Task（任务） | 一次具有输入、计划、资源预算、状态和结果的执行实例 | 将归档内的 JSON 提取并验证 |
| Evidence（证据记录） | 描述数据来源、检测结果、验证方式、推断与限制的结构化记录 | 文件格式识别结果、校验结果、REA 分析结论 |

**关键区分：** 字节读取不是格式解析；格式解析不是解压缩；解压缩不是密码学解密；解密成功也不必然表示内容可信。每一步都必须由明确的能力与结果语义表达。

## 3. 逻辑架构与模块边界

### 3.1 核心模块

1. **Core Runtime**：创建和关闭引擎实例，管理生命周期、配置、线程与总体资源预算。
2. **Data I/O**：定义字节源、写入端、读取语义与访问能力。
3. **Capability Registry**：注册、查询、版本约束、冲突检测和能力健康状态。
4. **Inspector / Detector**：识别可能的格式、编码与容器；输出证据和置信信息，不擅自执行高风险操作。
5. **Planner**：检查输入/输出类型是否兼容，构建显式或建议性处理计划。
6. **Task Runtime**：调度任务图、取消、超时、重试策略、状态跟踪、资源核算与结果收集。
7. **Buffering & Flow Control**：有界队列、缓冲池、背压、可选预读与数据块生命周期管理。
8. **Error & Observability**：结构化错误、阶段追踪、指标、诊断事件和可复现的测试记录。
9. **Storage Manager（分阶段实现）**：管理逻辑对象与物理布局之间的映射；具体存储后端作为适配模块。
10. **Adapters**：连接 7-Zip/压缩库、FFmpeg、SQLite、格式解析器、密码学库和 REA 等外部能力。

### 3.2 不应发生的耦合

- Core 不应包含每一种格式的解析逻辑。
- 压缩模块不应承担通用文件系统、元数据事务或网络协议管理职责。
- Detector 不应因为“看起来像某格式”就自动执行宏、脚本或有副作用的内容。
- 存储层不应假设所有数据都必须经过压缩。
- AI/REA 不应成为普通读取请求的必经步骤。
- 外部库的特有类型不应泄漏到所有公共 Core API 中；应由适配层转换为项目自己的稳定类型。

### 3.3 控制面与数据面

概念上分开两类操作：

- **控制面**处理配置、能力发现、计划、任务状态、权限、取消和诊断。
- **数据面**传递字节块、帧、消息、解析结果等实际内容。

这不强制要求它们一开始就运行在不同进程。MVP 可以单进程实现，但接口应避免把大型数据反复复制进控制面消息。

## 4. 数据源与写入端契约

### 4.1 设计原则

1. **读操作要明确区分随机访问与顺序访问。** 不能假设网络流、管道和文件都有相同能力。
2. **短读不自动等于错误。** 在顺序流或某些 I/O 后端中，一次读取可能少于请求长度；调用者应基于返回的实际字节数、EOF 与错误状态继续处理。
3. **随机读取必须明确语义。** `read_at(offset, ...)` 不应隐式依赖共享的可变游标；在后端支持时，同一源可安全执行多个不重叠的随机读取。
4. **EOF 与失败必须分开表达。** 正常结束不是 I/O 故障。
5. **资源所有权必须清楚。** 源关闭之后，不得继续使用其句柄或借用缓冲区。
6. **源的能力必须可查询。** 不支持随机访问的源不能被伪装成支持随机访问。
7. **I/O 后端应可注入。** 方便测试内存源、损坏源、慢源、限流源与故障源。

### 4.2 建议的数据源能力

`SourceCapabilities` 至少表达：

- `sequential_read`
- `random_read`
- `known_size`
- `seek`
- `stable_content`（读取期间内容是否被约定为稳定）
- `concurrent_reads`
- `async_io`
- `seek_cost_class`（低/中/高/未知，提示调度优化）

能力必须反映真实后端条件。比如网络响应可以是顺序可读，但不一定支持随机访问；远程对象可能支持按范围读取，却存在较高的随机访问延迟。

### 4.3 语言无关的接口草案

```text
ByteSource
  describe() -> SourceDescriptor
  read_next(max_bytes, context) -> ReadResult          # 仅支持顺序读取的源使用
  read_at(offset, max_bytes, context) -> ReadResult   # 仅支持随机读取的源使用
  close() -> Result

ReadResult
  bytes_read: integer
  eof: boolean
  buffer_or_data: ByteSlice
```

以上是语义示例，不要求最终实现采用这种确切方法签名。接口需通过能力声明或类型系统阻止对不支持的读取模式进行调用。

### 4.4 随机读取规则

- `offset` 不得为负数。
- 返回数据长度不得超过调用者请求的上限。
- 返回 `bytes_read = 0` 且 `eof = false` 不得在无进展的情况下无限循环；应由运行时限制连续无进展次数并产生可诊断错误。
- 并发读取的安全性必须由源能力声明；不安全的后端由适配器串行化。
- 若源内容在读取过程中可能变化，必须有快照、版本或不稳定内容的明确标记，避免结果混合了不同版本。

### 4.5 写入端与提交规则

```text
ByteSink
  describe() -> SinkDescriptor
  write(bytes, context) -> WriteResult
  flush(context) -> Result
  commit(context) -> Result
  abort() -> Result
  close() -> Result
```

需要区分：

- `flush`：将后端缓冲推进到其定义的持久化边界，但不一定代表整个对象发布成功。
- `commit`：确认输出完整并使对象可见，具体原子性取决于后端契约。
- `abort`：尽力放弃未提交输出并清理临时资源。

若目标后端不支持原子提交，必须在 `SinkDescriptor` 中明确说明；Core 不得虚构后端并不具备的原子性。

## 5. 统一能力描述（Capability Descriptor）

### 5.1 能力必须声明什么

每个可调用能力至少声明：

- 稳定的能力 ID 与版本，例如 `compression.zstd`、`text.decode.utf8`、`container.parse.zip`。
- 输入类型与输出类型。
- 参数定义与默认值。
- 是否允许流式处理、随机访问、增量处理与并发调用。
- 是否有损、是否确定性、是否修改外部状态。
- 需要的资源类别与可配置限制。
- 失败类别、取消行为、超时行为。
- 可提供的格式识别或完整性验证证据。
- 适用平台与可选依赖信息。

### 5.2 初版能力类别

```text
inspect       格式/编码/容器探测
parse         结构解析
encode        编码或序列化
decode        解码或反序列化
compress      压缩
 decompress   解压
encrypt       加密
 decrypt      解密
verify        校验、认证或结构验证
transcode     格式/表示转换
index         创建或使用索引
store         持久化与布局管理
analyze       分析与提取信息
```

实际枚举在实现时应统一命名；上列仅用于说明类别。`decode` 不应覆盖所有操作的语义。能力 ID 需要精确到格式、算法或有明确版本的行为，避免只有一个含义模糊的 `decode.anything`。

### 5.3 类型描述

建议用 MIME 类型、项目命名的语义类型以及版本化格式 ID 的组合描述数据。例如：

- `bytes/raw`
- `text/utf-8`
- `document/json`
- `archive/zip`
- `compression/zstd-frame`
- `media/video-frame`
- `network/http-message`
- `crypto/ciphertext`

这些是项目内部的类型标签示例，不宣称它们全都是标准 MIME 类型。

类型还应允许附加参数，例如字符集、容器版本、时间基准、字节序、压缩字典 ID 或协议版本。附加参数不能靠自由文本随意比较；应采用可验证的结构化字段。

### 5.4 示例：能力描述对象

以下为概念示例，不是最终冻结的 JSON Schema：

```json
{
  "id": "compression.zstd",
  "version": "1.0",
  "category": "compress",
  "inputs": ["bytes/raw"],
  "outputs": ["compression/zstd-frame"],
  "features": {
    "streaming": true,
    "random_access": false,
    "incremental": false,
    "lossy": false,
    "deterministic": true,
    "side_effects": false
  },
  "parameters": {
    "level": { "type": "integer", "default": 3, "range_validation": "delegated_to_backend" }
  },
  "resource_hints": {
    "memory_class": "configurable",
    "cpu_class": "medium"
  },
  "security": {
    "requires_secret": false,
    "verifies_integrity": false
  }
}
```

压缩级别的有效范围由实际绑定的后端库与版本校验；示例中的 `range_validation` 是概念字段，不是标准 JSON Schema 关键字。正式 Schema 应使用扩展规则或由适配器生成与后端版本一致的约束。

### 5.5 能力注册规则

- 相同 `id` 的不兼容实现不能被静默覆盖；必须用版本或实现标识区分。
- 注册时校验必填字段、参数 schema、输入输出类型、依赖状态与能力声明。
- 模块声明的功能需由一致性测试验证，不能只信任自报的 `random_access=true` 等字段。
- 能力缺失、版本冲突或依赖不可用必须能被查询，并提供明确诊断。
- 第三方插件在核心进程内运行之前，应评估其稳定性和权限；高风险、容易崩溃或不可信的插件未来可隔离到子进程。

## 6. 任务、执行计划与处理图

### 6.1 任务由什么组成

```text
TaskSpec
  task_id
  inputs[]
  plan
  outputs[]
  parameters
  resource_budget
  deadline
  cancellation_token
  trust_policy
  metadata
```

Task 应引用输入对象，而不是把无限大的文件内容直接复制进任务描述。计划中的节点通过类型化的输入输出连接，实际字节块在数据面流动。

### 6.2 执行图规则

- 计划默认是有向无环图（DAG）；确有循环需求时，必须用显式的迭代节点与终止条件表达，不允许隐藏无限循环。
- 每个边都声明其承载的数据类型或表示形式。
- 每个节点声明输入数量、输出数量、资源需求、取消语义与副作用。
- Planner 在执行前尽可能发现类型不匹配、缺失参数、缺失能力和不可满足的访问需求。
- 自动识别只产生“建议计划”；遇到歧义、危险操作或密钥需求时，应要求显式策略或用户提供必要信息。
- 不得从文件内容、网页、反编译结果或协议负载中读取指令来覆盖 Core 的系统策略。

### 6.3 示例处理计划

```text
ByteSource
   │
   ▼
Container Inspector
   │ 识别出候选容器，并记录依据与置信信息
   ▼
Container Reader
   │ 提取一个明确的成员流
   ▼
Decompressor（如该成员确实是压缩数据）
   │
   ▼
Text Decoder（如检测/用户配置确认字符编码）
   │
   ▼
Document Parser（如 JSON/XML 等）
   │
   ▼
ByteSink / Data Object / Analysis Result
```

这不是固定的万能流水线。若输入本身就是 UTF-8 文本，就不需要经过容器读取或解压；若处理的是视频，则应选择媒体容器与媒体解码能力。

### 6.4 显式模式与自动模式

- **显式模式：** 调用方指定格式、算法或处理步骤；系统验证参数、资源与类型是否可行。
- **自动模式：** 系统可执行低风险检测并提出计划；对无法可靠区分的格式，应保留候选项及证据，不能假装确定。
- **安全敏感操作：** 解密、密钥使用、执行外部程序、访问受保护资源或有副作用的操作必须经过明确授权策略。

## 7. 任务状态机与取消行为

### 7.1 任务状态

建议状态：

- `ACCEPTED`：请求已接收。
- `VALIDATING`：检查输入、参数、权限、能力与预算。
- `PLANNED`：执行计划已构建并通过预检查。
- `QUEUED`：等待调度资源。
- `RUNNING`：一个或多个节点正在执行。
- `WAITING_IO`：因输入/输出暂时不可用而等待。
- `CANCEL_REQUESTED`：已接收取消请求，正在停止工作与清理。
- `SUCCEEDED`：成功完成并满足输出提交规则。
- `FAILED`：执行失败。
- `CANCELED`：取消结束，按契约完成清理。

`SUCCEEDED`、`FAILED` 与 `CANCELED` 为终态。`WAITING_IO` 与 `RUNNING` 之间可以多次转换。实现可以在内部增加更细状态，但公共状态需要保持稳定。

### 7.2 允许的主要转换

```text
ACCEPTED → VALIDATING → PLANNED → QUEUED → RUNNING
                                      ↕          ↕
                                  WAITING_IO ─────┘

任意非终态 → CANCEL_REQUESTED → CANCELED
任意非终态 → FAILED
RUNNING → SUCCEEDED
```

若在运行中请求取消，节点必须检查取消令牌，停止接收新工作、释放未提交的临时资源，并按输出端契约执行 `abort`。无法中断的第三方调用必须有已记录的限制；必要时未来采用子进程隔离。

### 7.3 成功标准

任务只有在所有必需节点成功、数据校验达到计划要求、必需输出完成 commit、最终结果可读取后，才能进入 `SUCCEEDED`。仅仅“处理函数返回”并不一定表示任务成功。

### 7.4 重试规则

- 仅对被标记为可重试的错误进行自动重试。
- 有副作用的操作默认不自动重试，除非提供幂等键或确认重试安全。
- 重试次数、退避上限与总 deadline 必须受控。
- 不可恢复的格式错误、认证失败、密钥错误或参数错误不应无限重试。

## 8. 统一错误模型

错误必须是结构化对象，不依赖解析错误文本。

```text
GsadError
  category
  code
  message
  stage_id
  task_id
  input_id (optional)
  byte_offset (optional)
  retryable
  recoverable
  details (structured, bounded)
  cause (optional, sanitized)
```

### 8.1 初版错误类别

- `INVALID_ARGUMENT`：参数非法或缺失。
- `UNSUPPORTED_CAPABILITY`：没有可用能力处理请求。
- `TYPE_MISMATCH`：计划节点的输入输出类型不兼容。
- `FORMAT_DETECTION_AMBIGUOUS`：检测结果不能可靠确定。
- `MALFORMED_INPUT`：输入格式不符合要求。
- `INTEGRITY_CHECK_FAILED`：校验和或完整性检查失败。
- `AUTHENTICATION_FAILED`：密码学认证失败。
- `KEY_REQUIRED` / `KEY_INVALID`：缺少密钥或密钥无效。
- `RESOURCE_LIMIT_EXCEEDED`：超过内存、输出体积、深度、CPU 或时间限制。
- `IO_ERROR`：底层 I/O 错误。
- `TIMEOUT`：达到 deadline。
- `CANCELED`：任务按取消流程终止。
- `PERMISSION_DENIED`：访问或能力未获授权。
- `DEPENDENCY_UNAVAILABLE`：依赖库或外部服务不可用。
- `PLUGIN_FAILURE`：适配器/插件运行失败。
- `OUTPUT_COMMIT_FAILED`：输出未能按要求提交。
- `INTERNAL_ERROR`：未分类的内部故障，必须附带诊断 ID。

`message` 供人阅读；`category` 和 `code` 供程序逻辑使用。`details` 必须有大小上限，并避免包含密钥、认证令牌或整段敏感输入。

---

## 9. 资源管理、缓存与背压

### 9.1 资源预算

每个任务至少可设置：

- 最大工作内存；
- 最大输出字节数；
- 最大输入读取量（可选）；
- 最大处理时间或 deadline；
- 最大并发节点数；
- 最大容器嵌套深度；
- 最大成员/帧/消息数量（按能力适用）；
- 最大字典、索引和元数据占用。

不能只依赖“压缩比限制”来防止解压炸弹。必须同时限制绝对输出大小、内存、时间与容器层数。默认应当有限，调用方要扩大预算时必须有明确配置。

### 9.2 缓冲和背压

- 每个队列都必须有明确上限，最好同时约束字节数与元素个数。
- 缓冲池占用计入任务或引擎资源预算；不能因任务数量增加而无限扩张。
- 消费端处理变慢时，生产端应等待、降低生产速度或取消，不能继续无限堆积。
- 取消任务时，必须释放排队但尚未处理的数据及不再需要的缓冲。
- 双缓冲只是某些顺序流场景的优化选择，不是所有读取路径的硬性要求。
- 压缩数据缓存与解码后数据缓存要分开衡量，因为大小、复用价值和内存成本不同。

### 9.3 缓存键

缓存项必须由足以确定内容的键标识。可能包括：对象版本或内容哈希、字节范围、能力 ID/版本、参数、字典版本和必要的安全上下文。不得把不同密钥、不同算法参数或不同对象版本的结果误认为同一项。

---

## 10. 安全基线

1. 所有外部文件、网页、网络包、归档条目、数据库字段、反编译结果及 AI/REA 输出均视为不可信输入。
2. “格式探测成功”不等于“数据安全”；“解密成功”不等于“来源可信”。不同验证结果需分别记录。
3. 解压、解析和媒体处理须使用资源预算，并在超限时可控终止。
4. 对加密数据，优先使用经过审查的密码学库；认证加密必须验证认证标签后才能将明文作为可信结果交给后续阶段。不得自行发明加密算法。
5. 密钥和认证凭证不应出现在普通日志、错误详情、缓存键或诊断转储中。
6. 不默认执行归档中的脚本、宏、程序或协议内容中的命令。
7. 插件只应获得完成任务所需的最小权限；未来需要运行不可信插件时优先考虑进程隔离和操作系统级资源限制。
8. 输出发布应区分临时写入与成功提交；失败任务不得把半成品伪装成完整对象。

---

## 11. 存储管理需要遵守的接口原则

存储层暂时不冻结某一种物理格式，但必须预留以下概念：

- **Logical Object**：调用者认识的数据对象。
- **Representation**：对象的一种原始、压缩、加密或派生表示。
- **Extent / Chunk**：表示内的一段数据范围；可以是固定分块，也可以由专用格式决定。
- **Index**：由逻辑范围映射至物理位置、时间戳、成员或块的位置关系。
- **Metadata**：格式、版本、长度、校验、访问权限、来源及关联信息。
- **Commit Record**：记录一次对象更新何时成为可见状态。

逻辑 API 应允许一种对象有多个表示，也允许不同对象使用不同布局。某些对象可直接保存原始文件，某些对象可采用分块和压缩，媒体对象可使用关键帧或时间索引，数据库则继续由适合事务的后端管理。

早期可以采用 SQLite 作为本地元数据后端候选，但物理数据布局、数据包格式和事务恢复协议必须由系统的存储层规格独立定义。不能假设 SQLite 元数据事务与独立数据文件写入天然是同一个原子事务。

## 12. 公共 API 草案

以下为行为层面的候选入口；实际函数名需在语言选定后调整。

### 引擎与能力

```text
engine_create(config) -> Engine
engine_shutdown(engine, policy) -> Result
capability_list(engine, filter) -> CapabilityDescriptor[]
capability_get(engine, capability_id, version_policy) -> CapabilityDescriptor
```

### 输入与输出

```text
source_open(spec, context) -> SourceHandle
source_describe(source) -> SourceDescriptor
source_read_at(source, offset, max_bytes, context) -> ReadResult
source_close(source) -> Result
sink_open(spec, context) -> SinkHandle
sink_write(sink, bytes, context) -> WriteResult
sink_commit(sink, context) -> Result
sink_abort(sink) -> Result
```

若后端不支持某操作，应返回明确的 `UNSUPPORTED_CAPABILITY`，或在类型系统中令该操作不可用；不能暗中用高成本的全量读取伪装成真正的随机访问。

### 检测、计划与任务

```text
inspect(input_ref, inspect_policy, context) -> InspectionReport
plan_build(input_refs, requested_operations, plan_policy) -> ExecutionPlan
task_submit(plan, resource_budget, output_spec) -> TaskHandle
task_poll(task) -> TaskStatus
task_wait(task, deadline) -> TaskResult
task_cancel(task, reason) -> Result
task_result(task) -> TaskResult
```

### API 契约要求

- 所有可能阻塞的操作都必须能接受 deadline 或 cancellation context，或在接口层明确说明无法取消的限制。
- 返回对象要明确所有权和有效期。
- 错误采用稳定错误码，不用字符串比较。
- 对大量数据优先传递句柄、切片、迭代器或有界流，而不是一次性把全部数据放进普通返回值。
- 公开 API 不应暴露某个第三方库的私有结构体作为长期契约。
- ABI 和语言绑定可以稍后确定，但语义测试应在 API 固化前开始。

## 13. MVP 验收测试

第一版不以“支持了多少种格式”作为唯一成功标准，应优先验证核心语义。

### 13.1 I/O 正确性

- 内存源、本地文件源、短读源、慢源和模拟故障源都通过同一套接口测试。
- EOF 与 I/O 错误可区分。
- 随机读取不会被其他并发请求的游标影响。
- 不支持随机访问的源会明确拒绝，而非静默全量读取。

### 13.2 能力与计划

- 能力可以注册、查询、版本匹配和移除。
- 无效参数、类型不匹配和缺失能力在执行前尽可能被识别。
- 检测器能够报告候选结果与依据，不把低置信结果伪装成确定结果。
- 对明确输入的处理计划能在执行后给出可追踪的阶段记录。

### 13.3 任务生命周期

- 成功、失败、超时与取消均进入正确终态。
- 取消发生在运行中、等待 I/O、等待队列和准备提交时都有测试。
- 非幂等操作不在缺少策略的情况下自动重复执行。
- 输出未完成提交时，不会被报告为完整成功产物。

### 13.4 资源与安全

- 超出内存、输出大小、处理时间和嵌套深度时能受控失败。
- 有界队列在消费者变慢时不会无限增长。
- 错误与日志中不会泄漏测试密钥或模拟凭证。
- 损坏数据能得到结构化错误，不导致无限循环或进程失控。

### 13.5 可重复性与可观测性

- 同一测试输入、同一能力版本与参数能产生可解释的测试结果。
- 每个任务可查询阶段、耗时、读取/写入字节、缓存命中（如已实现）与失败原因。
- 性能测试记录环境、输入集、参数和版本；未经对照测试不宣称性能提升。

## 14. 建议的首个原型范围

首个可运行原型只需证明核心契约，不追求格式数量：

1. 一个 Engine Runtime。
2. 一个内存字节源、一个本地文件源、一个内存写入端和一个临时文件写入端。
3. 一个 `inspect` 能力，先能识别少量已知测试格式并报告未知格式。
4. 一个无操作/恒等转换能力，用于验证数据流与任务状态。
5. 一种成熟的无损压缩/解压适配能力，用于验证输入输出类型、资源上限和结果校验。
6. 一个明确的任务状态机和结构化错误模型。
7. 基本有界缓冲、取消和端到端测试。

完成以上内容后，再基于实测决定是否先扩展二进制解析、归档、文本、媒体、协议或专用存储。优先顺序应由实际使用场景、风险、成熟度与测试结果决定，而不是按模块名称堆叠。

## 15. 需要评审的开放决策

以下问题应通过小型实验、技术评审或 ADR（Architecture Decision Record）逐一决定：

1. **开发语言：** 对内存安全、FFI、异步 I/O、生态、性能、跨平台与开发效率做对照原型。
2. **模块边界：** 首版全部采用同进程模块，还是把特定第三方能力放入子进程。
3. **插件 ABI：** 内部接口成熟前不要冻结；之后比较 C ABI、进程 RPC、WASM 等边界。
4. **并发模型：** 比较线程池、异步 I/O、任务图调度与混合模式的实际复杂度。
5. **数据缓冲所有权：** 比较复制、引用计数切片、池化缓冲和借用生命周期方案。
6. **错误码版本策略：** 确定稳定类别、扩展码和对外语言绑定规范。
7. **元数据后端：** SQLite 是候选之一；需根据事务、部署和并发需求评估。
8. **自有存储格式：** 只有在具体需求与现成格式之间存在可证明的差距时才启动正式设计。
9. **默认安全预算：** 根据部署形态、任务类型和威胁模型定出可配置的默认值。
10. **性能基准：** 建立代表性数据集和基线，再制定可量化目标。

每个决策记录应至少包含：背景、需求、候选方案、评价标准、实验结果、结论、代价、回滚或迁移方案。

完成本规格评审后，下一阶段应产出：

1. **ADR-0001：主开发语言与 FFI 策略。**

## 结论

GSAD 的核心不是让所有格式都经过同一种解码流程，而是建立一套可靠的共同基础：数据源有明确语义，能力可以描述和验证，任务可以规划、限制、取消与诊断，数据可以通过有界通道传输，物理存储可以因数据特征而异。

专业算法允许多样化，基础契约则必须清晰、稳定、可测试。这是后续深度整合压缩、媒体、文本、网络协议、密码学、二进制分析、存储与 AI 能力的前提。
