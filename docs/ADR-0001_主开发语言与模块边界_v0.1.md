# ADR-0001：主开发语言与模块边界

- **项目：** GSAD（Generalized Stray-Arrow Decoding，项目名称已通过 ADR-0003 确立）
- **状态：** 建议接受（Proposed / Ready for Review）
- **版本：** 0.1
- **日期：** 2026-10-20
- **决策范围：** 核心运行时、内部模块接口、外部引擎适配方式、插件边界
- **不在本 ADR 范围：** 最终自有存储格式、每一种压缩算法的选择、产品 UI、云端部署形态

## 1. 决策摘要

**建议将 Rust 作为 GSAD 核心运行时的主要实现语言；将 C ABI 作为原生外部引擎的主要进程内边界；将子进程/RPC 作为高风险、易崩溃或需要独立依赖环境的扩展边界。**

C/C++ 代码可以用于必要的薄适配层或经过评估的专业引擎，但不要求所有模块重写为 Rust，也不允许外部 C/C++ 库的内部数据结构成为 GSAD 的公共核心模型。

内部 Rust 模块可以使用 Rust 类型和 trait 协作；但**不可把 Rust 原生 ABI 直接当作跨版本、跨编译器的稳定插件 ABI**。对外 ABI 必须明确版本、数据布局、所有权、错误和生命周期。

此决定的目标不是追求某一种语言的纯粹性，而是让核心调度、资源管理、错误处理和数据契约可控，同时保留成熟专业库的性能和覆盖面。

## 2. 项目约束回顾

GSAD 是通用数据处理与存储引擎，不是单一压缩器、媒体播放器或 AI 框架。长期范围可能包含：

- 原始字节、文本、源码和文档；
- 结构化二进制与自定义文件格式；
- 压缩、解压、归档、分块、去重与校验；
- 图片、音频、视频和媒体容器；
- 网络协议解析、分帧与流重组；
- 编码转换、密码学操作与认证验证；
- 多种物理存储布局、索引、缓存、并发访问和崩溃恢复；
- 后续可选的 REA 分析能力、AI 工具调用和语义索引。

因此，语言决策必须同时考虑内存安全、底层 I/O、并发、跨平台构建、原生库互操作、测试和长期维护，而不能只比较单次算法 benchmark。

## 3. 候选方案比较

| 维度 | Rust 核心 | C++ 核心 | Go 核心 |
|---|---|---|---|
| 底层性能与内存布局控制 | 强 | 强 | 较强，但某些低层场景限制更多 |
| 内存安全默认保障 | 较强；不安全代码和 FFI 仍需审查 | 依赖编码纪律、工具和审查 | 内存安全机制较成熟，但手动布局/零拷贝场景需权衡 |
| 并发与资源生命周期表达 | 所有权、借用与类型系统有帮助 | 能力强，但需要团队规范 | goroutine/channel 易用；细粒度资源和零拷贝控制需设计 |
| 接入 FFmpeg、SQLite 等 C API | 可通过 C ABI/绑定接入，需隔离 unsafe 边界 | 直接接入较方便 | 可通过 cgo 接入，但引入跨语言调用和构建成本 |
| 接入 C++ 专用库 | 需要窄 C ABI shim 或子进程边界 | 较方便 | 通常需要 C ABI shim 或子进程边界 |
| 插件跨版本 ABI | 需要自行制定稳定 ABI；Rust ABI 不直接作为承诺 | 同样需要自行制定 ABI | 对外原生插件也需明确接口形式 |
| 开发复杂度 | 学习和异步/生命周期设计有成本 | 语言机制丰富，内存与并发风险管理负担较高 | 上手较快，但并非所有低层需求都最合适 |
| 适合作为 GSAD 核心 | **推荐** | 可行备选 | 适合未来服务层或工具，不作为首选底层核心 |

这张表是针对 GSAD 约束的工程判断，不是对语言的一般排名。最终仍应由构建原型、性能测试和团队实际能力校验。

## 4. 选择 Rust 核心的理由

1. GSAD 会处理大量来自外部的不可信字节与复杂格式，内存安全默认机制有助于降低一类常见错误风险。
2. 核心需要管理有界缓存、异步 I/O、取消、并发任务和资源生命周期，Rust 的所有权模型能帮助表达这些约束。
3. 核心数据模型和调度机制应独立于 FFmpeg、SQLite、压缩库或某一种格式的私有对象。
4. Rust 可以通过明确定义的 C ABI 与成熟 C 库协作，避免为追求语言统一而重写已成熟的媒体、压缩或密码学实现。
5. Rust 官方平台支持按 target tier 定义保证程度；目标平台应在项目需求中明确，并通过 CI 实际验证，不能把“理论上可编译”视为完全支持。

- Rust 平台支持与 target tier：https://doc.rust-lang.org/rustc/platform-support.html

## 5. 主要代价与缓解办法

### 5.1 Rust 学习与建模成本

生命周期、trait、异步任务与并发边界需要审慎设计。第一版不应把所有模块都做成复杂的泛型框架；优先使用清晰的具体类型和少量稳定抽象。

### 5.2 原生库互操作成本

不同平台的 C/C++ 编译器、链接方式、系统库和预编译二进制可能产生维护成本。每个原生依赖必须记录版本、许可证、构建方法、目标平台和测试状态。

### 5.3 unsafe 与 FFI 风险

将 unsafe 尽可能限制在小型 adapter crate 或 shim 内。公共 Rust API 不暴露原始指针；外部缓冲区需要明确长度和所有权；任何跨越 C ABI 的函数不得让 Rust panic 或 C++ exception 未定义地穿越边界。

### 5.4 并非所有库都适合进程内加载

如果某个解析器风险高、依赖复杂、崩溃影响大或许可证/构建条件特殊，可先通过子进程协议接入。进程隔离不是所有模块默认方式，而是明确的安全与可靠性选项。

## 6. 模块边界决策

### 6.1 `gsad-core`

负责稳定的核心类型和规则：

- `ObjectId`、`SourceId`、`TaskId`、`CapabilityId` 等标识；
- 统一错误类别和可恢复性；
- 数据源与数据目标的最小契约；
- 能力描述、任务计划与任务状态；
- 取消、超时、预算、审计上下文；
- 公共版本规则。

不得依赖 FFmpeg、SQLite 或某个压缩器的专用类型。

### 6.2 `gsad-runtime`

负责任务执行：

- 任务图验证和调度；
- 并发与资源预算；
- 有界缓冲、背压、取消传播；
- 超时、重试策略（仅对明确可重试操作）；
- 日志、指标、追踪和故障隔离；
- 任务输出的临时区与提交阶段。

Runtime 可以使用异步 I/O，但底层数据契约不应被设计成只能在某一个异步执行器里工作。

### 6.3 `gsad-io`

负责数据源与数据目标抽象：

- 本地文件、内存缓冲、受限的流、后续网络/对象存储；
- 顺序读取与可选随机读取能力；
- 明确区分 EOF、短读、取消、暂时不可用和真正 I/O 错误；
- 读取与写入能力分开描述；
- 对随机访问声明长度与偏移语义；
- 写入阶段区分临时写入、flush/sync 和最终提交。

不可随机访问的数据源不能伪装成可随机访问的文件；适配器必须如实声明能力。

### 6.4 `gsad-capabilities`

负责能力注册与选择，不直接把文件扩展名等同于格式事实。能力描述至少包括：

- 输入和输出数据类别；
- 操作类型（识别、解析、编码、解码、压缩、解压、加密、解密、校验、转换）；
- 必需参数与可选参数；
- 流式、增量、随机访问和并发能力；
- 可预测的内存/CPU/输出规模限制；
- 可信度、格式探测分数和支持范围；
- 版本、依赖和许可证元数据。

格式探测的结果只是候选证据；真正处理时仍应检查格式头、参数和输入有效性。

### 6.5 `gsad-storage`

负责逻辑对象和物理布局之间的分离：

- 逻辑对象、块、索引和版本映射；
- 对象后端与布局策略接口；
- 完整性校验与恢复清单；
- 缓存策略的对接点；
- 原始布局、分块布局和未来专用布局的实验接口。

第一阶段不承诺最终的 GSAD 自有容器格式。SQLite 可以作为本地元数据后端候选，但它不是逻辑对象模型，也不决定数据包的物理布局。

### 6.6 `gsad-codecs`

定义通用压缩/编码/解码契约，不把所有处理行为塞到一个 `decode()`：

- 压缩和解压是独立操作；
- 字符集解码与结构解析分开；
- 媒体解码单独建模；
- 密码学解密必须处理认证结果与密钥来源；
- 对未知、损坏、截断或参数不兼容的数据返回明确错误；
- 输出大小和内存使用受到预算限制。

算法以 provider 形式接入；初期优先接入成熟实现，性能热点或目标缺口经测量后再决定是否自研或深度修改。

### 6.7 外部适配器

建议每个重要原生依赖一个独立适配器：

- `adapter-ffmpeg`：用 FFmpeg C API 与 AVIO 自定义 I/O 对接 GSAD 数据源；媒体时间戳和解码状态保留在媒体域，不强行转换成通用文件语义。
- `adapter-sqlite`：封装元数据、索引或事务后端；连接的线程使用规则必须明确，不能把 SQLite WAL 当作跨主机协调机制。
- `adapter-lzma-sdk`：视选定组件和用途接入 LZMA/7z 相关算法；区分算法 SDK 与完整 7z 归档实现。
- `adapter-crypto`：只接入经过审查的成熟密码学实现，不自行发明密码算法。
- `adapter-rea`：后续通过独立任务协议调用 REA，并把输出规范化为带来源、证据与限制的分析结果。

每个 adapter 必须翻译错误、内存所有权、取消、资源限制和生命周期；不应只把外部函数名映射成 GSAD 函数名。

## 7. 插件边界

采用三级扩展模型：

1. **内置 Rust 模块：** 同一工作区内使用 Rust trait/类型；这属于内部实现接口，不承诺跨 Rust 版本的稳定二进制 ABI。
2. **原生进程内插件：** 只有确有必要时采用版本化 C ABI。仅暴露不透明句柄、固定宽度整数、明确长度的字节缓冲区、版本信息和错误码。分配方负责释放其分配的内存，不允许双方对同一块内存随意释放。
3. **进程外插件：** 面向高风险解析器、崩溃风险较高的库、独立运行环境或需要隔离依赖的工具。协议必须限定消息大小、超时、权限、输出与资源使用。

插件 ABI 最少包含 `abi_major`、`abi_minor`、能力标识、创建/销毁入口、操作入口、错误信息接口和可选取消入口。主版本不兼容时拒绝加载，不进行猜测性调用。

## 9. 构建与质量门槛

- 统一使用 Cargo workspace 管理 Rust 模块；只有实际需要时才引入 C/C++ 构建系统。
- CI 初期至少覆盖目标开发平台及主要构建模式；平台范围必须明示，而不能无条件宣称全平台支持。
- 对外部依赖记录精确版本、来源、许可证、构建参数和安全更新流程。
- 核心数据类型必须有单元测试和属性测试；输入解析器必须有畸形输入测试。
- 为原生适配器测试短读、错误返回、取消、超时、重复销毁、异常返回和资源释放。
- 对解压设置输出大小、扩展比、字典内存、CPU 时间和递归深度等限制。
- 加密输出必须验证认证标签后才能向调用方交付为已认证的明文；不得忽略认证失败。
- 存储测试覆盖写入中断、崩溃恢复、孤立块、校验错误和版本迁移。
- 性能判断必须使用可重复 benchmark，分别测吞吐、延迟、峰值内存、CPU、随机读取和并发退化。

## 10. MVP 技术选择建议

首个可运行版本不追求覆盖全部格式。建议先完成：

1. 本地文件和内存数据源；
2. 一个简单的 Rust 内置能力示例；
3. 一个成熟通用无损压缩 provider；
4. 一个格式/文本解析处理路径；
5. 统一任务状态、取消、错误、资源预算与日志；
6. 契约测试和 benchmark harness；
7. 最小 CLI，用于检查数据、执行处理任务和输出统计。

FFmpeg、REA、复杂网络协议、完整自有存储容器格式暂不成为 MVP 的阻塞项。先证明抽象成立，再逐个加入真实的外部引擎。

## 11. 决策验收标准

以下条件达到后，才将本 ADR 从“建议接受”转为“已接受”：

- 团队能够在目标开发平台稳定编译和运行 Rust workspace；
- 至少一个外部 C API 适配器通过端到端测试；
- 原生错误、取消、缓冲区所有权和释放责任有测试覆盖；
- 同一数据处理流程能够替换 provider，而无需修改核心任务模型；
- 核心 crate 不依赖具体媒体、压缩、数据库或 AI 引擎；
- 性能与内存基线可重复测量；
- 第三方许可证和构建流程已经记录。

## 12. 未决问题

以下事项在原型之后另立 ADR，不在此处抢先决定：

- 具体异步运行时及线程池策略；
- 动态原生插件是否为正式需求；
- 公共 C ABI 的完整定义和稳定策略；
- 第一个正式支持的操作系统及 CPU 架构列表；
- SQLite 是否作为 MVP 元数据后端；
- 首个压缩 provider 及其参数策略；
- 是否引入 C++ 核心子模块，或仅用 C ABI shim；
- 自有存储格式是否必要，以及版本演进协议。
