# ADR-0002：流式输出与提交边界

- 状态：原型阶段采纳，尚未承诺为稳定公共 API
- 日期：2026-10-20
- 影响范围：`gsad-core` 的引擎执行与输出接口

## 背景

原始 `EngineOutput` 通过 `Vec<u8>` 返回完整输出，会要求输出全部驻留内存，不适合大型解压结果、媒体处理、长流和大型数据集。与此同时，若引擎自己直接打开最终目标并提交，核心就难以统一落实资源限制、取消及失败清理。

## 决策

1. 增加 `OutputWriter`，作为引擎写出增量数据的受限接口。
2. 增加 `OutputSink`，作为宿主拥有生命周期控制权的目标接口。
3. 由 `BoundedOutputWriter` 在写入边界落实 `max_output_bytes` 与协作式取消检查。
4. 由 `execute_to_sink` 执行契约验证，并统一管理 `flush -> commit` 与失败后的 `abort`。
5. 使用 `CommitSemantics` 明确区分原子提交、尽力清理和不可逆输出，避免对所有目标承诺同等的回滚能力。
6. 保留 `EngineOutput` 供小型结果使用；默认 `execute_to` 提供兼容适配，但大型输出引擎必须覆写 `execute_to`。

## 考虑过的替代方案

### 方案 A：继续仅返回 `Vec<u8>`

优点是接口简单；缺点是大输出内存占用不可控，因此不采纳为唯一执行路径。

### 方案 B：将最终文件路径传给引擎

优点是引擎可以直接写文件；缺点是职责泄漏、平台语义耦合，且核心无法可靠控制提交和清理，因此不采纳为通用契约。

### 方案 C：让引擎直接获得带有 commit/abort 的 sink

这种方式容易让引擎过早提交或在执行失败时遗漏清理。原型选择把写入权限与提交权限分开。

## 后果与约束

- 引擎应按合理大小写入块，减少取消延迟；同步 sink 的阻塞行为可以形成自然背压，但跨任务异步队列和有界缓冲池仍未实现。
- 输出字节上限在写入边界强制执行。旧的 `execute` 实现仍可能先在内存中构造超限结果，因此不能被视为大文件安全实现。
- `abort` 为尽力清理；只有声明并实现原子语义的 sink 才可以给出相应保证。
- 核心没有对原生引擎进行进程隔离，也无法强制终止无响应的函数调用。
- 后续需要真实文件 sink、崩溃/故障注入测试及跨平台构建验证，再决定此 API 的长期稳定性。

## 验收

`tests/output_contracts.rs` 应覆盖短写、输出超限、取消、输出类型不符、引擎失败、刷新失败、提交失败及 abort 行为。所有目标实现还需另行测试其提交语义。
